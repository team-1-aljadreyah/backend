# Security Audit & Architecture Review Report
**Project:** Al-Jadreyah Clinic Management System Backend  
**Audit Date:** November 8, 2026  
**Auditors:** Principal Backend Engineer & DevSecOps Architecture Team  
**Scope:** Backend codebase, database models, security dependencies, services, integrations, infrastructure configurations, and tests.

---

## 1. Executive Summary

A comprehensive, end-to-end audit was conducted across the backend codebase of the Al-Jadreyah Clinic Management System. The review identified 28 distinct vulnerabilities and architectural defects spanning authentication bypasses, insecure session management, Broken Object-Level Authorization (BOLA/IDOR), unauthenticated medical file exposure, unverified financial transactions, race conditions in queue and pharmacy inventory management, schema inconsistencies, and missing real-time capabilities.

Remediation has been designed and implemented in strict compliance with healthcare data protection principles, ACID transactional integrity, and production readiness requirements.

## 2. Comprehensive Issue Inventory

| **SEC-01** | Critical | Security | `app/core/security.py` | `decode_token` | Hardcoded bypass accepting `mock-token-{id}` and `mock-refresh-{id}` | Complete authentication bypass; arbitrary user/manager impersonation without secret key | Remove mock token checks entirely; require valid cryptographic signature on all tokens via PyJWT | `test_jwt_mock_token_rejected` | Fixed |
| **SEC-02** | Critical | Security | `app/services/auth_service.py` | `login`, `change_password` | Hardcoded dictionary `seed_passwords` (`Manager123!`, `password123`, etc.) accepted unconditionally | Unauthorized account takeover for any account regardless of actual stored password | Eliminate `seed_passwords` bypass; enforce cryptographic password verification on all attempts | `test_seed_password_bypass_eliminated` | Fixed |
| **SEC-03** | High | Security | `app/core/security.py` | `verify_password`, `get_password_hash` | PBKDF2 without modern memory-hard hashing; plaintext comparison fallback | Weak hash protection against GPU cracking; accidental plaintext password persistence | Upgrade to Argon2id password hashing with automatic transparent migration of legacy hashes | `test_argon2id_hashing_and_migration` | Fixed |
| **SEC-04** | High | Security | `app/core/dependencies.py` | `get_current_user_optional` | Does not validate JWT `type` claim (`access` vs `refresh`) | Long-lived refresh tokens can authenticate ordinary protected REST API routes | Verify `payload.get("type") == "access"` in authentication dependency; reject refresh tokens | `test_refresh_token_cannot_access_protected_routes` | Fixed |
| **SEC-05** | High | Security | `app/services/auth_service.py` | `forgot_password`, `reset_password` | In-memory ephemeral dict `_reset_codes` and mismatch with Supabase OTP | OTPs lost on multi-worker restarts; user receives Supabase SMS code but system compares local random code | Implement persistent, cryptographically secure hashed OTP storage in database/Redis with rate limits and attempt tracking | `test_otp_persistence_and_brute_force_protection` | Fixed |
| **SEC-06** | High | Security | `app/services/auth_service.py` | `register` | Patient account links walk-in patient record based solely on submitted phone number | Attacker registering a patient's phone number automatically inherits private medical history without identity verification | Require identity matching (normalized name + DOB confirmation) or staff verification before linking walk-in records | `test_registration_unverified_record_linking_prevented` | Fixed |
| **SEC-07** | High | Security | `app/services/auth_service.py`, `app/database/models/profile.py` | `refresh_tokens`, `logout` | Stateless refresh tokens without database tracking or revocation | Compromised refresh tokens cannot be revoked; logout does not invalidate active refresh tokens | Create `user_sessions` table; store SHA-256 token hashes; rotate refresh tokens and revoke on logout/password change | `test_refresh_token_rotation_and_revocation` | Fixed |
| **SEC-08** | Critical | Security | `app/services/payment_service.py` | `get_patient_payment_history` | Query falls back to selecting all clinic patient IDs when staff calls `/me/payments` without `patient_id` | Reception, lab techs, or doctors calling `/me/payments` receive all clinic financial history | Restrict `/me/payments` exclusively to current user's own family records; require manager/accountant role for clinic-wide queries | `test_me_payments_cannot_leak_all_clinic_records` | Fixed |
| **SEC-09** | High | Security | `app/api/routes/patients.py` | `get_patient_alerts`, `get_patient_vitals`, `get_patient_history` | Role checks permit `reception` to query clinical history; doctors not verified against active/past doctor-patient relationship | Receptionists view private diagnoses, vitals, and visits; doctors view records of patients they have never treated | Enforce clinical RBAC: block reception from medical endpoints; verify doctor has had an appointment with the patient | `test_patient_privacy_reception_blocked_and_doctor_relationship` | Fixed |
| **SEC-10** | High | Security | `app/api/routes/patients.py` | `get_booking_rules` | Uses `get_current_user` without verifying patient ownership or staff authorization | Any authenticated patient can probe booking rules and penalty status of any other patient (IDOR) | Restrict to patient's own record or staff with reception/manager role | `test_booking_rules_idor_blocked` | Fixed |
| **SEC-11** | High | Security | `app/services/appointment_service.py` | `cancel_appointment`, `reschedule_appointment` | Non-patient check only tests `user.role == "patient"`, allowing any staff role (lab, pharmacy, accountant) to cancel or reschedule | Unauthorized staff cancel or reschedule patient consultations | Restrict cancellation and rescheduling to patient owner, assigned doctor, reception, or manager | `test_appointment_cancellation_role_enforcement` | Fixed |
| **SEC-12** | Critical | Security | `app/main.py` | StaticFiles mount at `/uploads` | `app.mount("/uploads", StaticFiles(directory="uploads"))` serves private medical documents publicly | Unauthenticated public access to sensitive patient lab results and social welfare certificates | Remove static mount; route all document downloads through authenticated, authorized controller endpoints | `test_uploads_static_files_disabled` | Fixed |
| **SEC-13** | High | Security | `app/integrations/supabase_storage.py` | `upload_file`, `create_signed_url` | Multi-year signed URLs (10 years) and MIME verification based only on client header | Sensitive documents remain accessible via leaked URLs for years; arbitrary malicious files uploadable | Enforce short-lived signed URLs (1-5 minutes); validate actual magic byte file signatures | `test_file_signature_validation_and_short_lived_urls` | Fixed |
| **SEC-14** | Critical | Security | `app/api/routes/payments.py` | `simulate_payment_outcome` | Public endpoint `/payments/{payment_id}/simulate` accessible in production by any authenticated user | Patients can forge successful payments for their appointments without paying | Restrict simulation exclusively to testing/development environments; disable in production | `test_payment_simulation_disabled_in_production` | Fixed |
| **SEC-15** | High | Security | `app/api/routes/payments.py` | `qi_payment_webhook` | Webhook takes raw payload without HMAC signature verification, timestamp, or replay protection | Attackers can forge webhook notifications and settle fake payments | Implement HMAC-SHA256 signature verification, replay protection with nonce/timestamp, and idempotent processing | `test_qi_webhook_signature_verification` | Fixed |
| **SEC-16** | High | Security | `app/integrations/qi_gateway.py` | `QiGateway.__init__` | Hardcoded sandbox credentials (`QI_SANDBOX_USERNAME`, etc.) in source code | Credentials leak to repository; production credentials cannot be safely injected | Load credentials strictly from environment variables; separate Sandbox and Production base URLs | `test_qi_gateway_environment_configuration` | Fixed |

| **FIN-02** | High | Business Logic | `app/services/appointment_service.py` | `cancel_appointment` | Inserts `Payment(kind="refund")` without payment provider API call or transaction confirmation | False completed refunds recorded in clinic books without actual money transfer | Support real provider refund API or transition to `refund_pending` state pending manual/provider approval | `test_refund_lifecycle_and_provider_call` | Fixed |
